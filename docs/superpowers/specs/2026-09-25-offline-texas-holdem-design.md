# Offline Texas Hold’em — Design Spec

Date: 2026-09-25

## Goal and constraints

Add a second, installable, offline pass-and-play game to the existing repository. Hearts stays at `/offline-hearts/`; Texas Hold’em lives at `/offline-hearts/offline-texas-holdem/` on the same GitHub Pages project site. Both paths are published together. Use one React/Vite/TypeScript project and share the deck, card rendering, roster, and storage utilities where possible. Preserve existing Hearts gameplay, its `hearts.game` and `hearts.history` records, and the `hearts.roster` player IDs and names.

Hold’em is a no-limit **tournament** for 2–8 distinct players on one device. Each starts with the same configurable positive integer chip stack. Configure a positive integer big blind at setup; the small blind is `ceil(bigBlind / 2)`. Blinds can be edited at any time, but a change during a hand takes effect on the next hand only. A player with zero chips is eliminated; the tournament ends when only one player has chips. Chips are virtual, with no money or payments.

## Shared architecture and deployment

- `src/shared/` owns the existing card model, unique 52-card deck, seeded shuffle, card-face component, player roster and roster persistence, and versioned localStorage helpers. Hearts imports these without changing public interfaces or persisted Hearts data. Hearts-specific points, sorting, passing, scoring, reducer, history, and UI remain Hearts-owned.
- `src/poker/engine/` contains pure TypeScript for five-card evaluation, best-five-of-seven selection, dealer and betting order, legal actions, side pots, payouts, and the tournament reducer. The engine never uses React or localStorage. Shuffle seeds and tournament IDs enter through actions.
- `src/poker/` also owns its screens, CSS, and independently versioned persistence (`poker.tournament` and `poker.settings`). The shared roster continues to use `hearts.roster`; poker does not write Hearts game or history keys.
- Vite builds two HTML entries and shared hashed assets under one project-site base of `/offline-hearts/`. The Hearts entry builds to `dist/index.html`; the Hold’em entry builds to `dist/offline-texas-holdem/index.html`. Their public URLs are `https://jamestenglish.github.io/offline-hearts/` and `https://jamestenglish.github.io/offline-hearts/offline-texas-holdem/`. Shared assets resolve relative to the project base from either page. Both pages have distinct manifests and iOS Home Screen icons/names; each offline entry and its required assets are precached, with navigation to either installed page working offline. Service-worker scope must cover both URLs without letting one app's manifest or icon install the other game. The existing Pages workflow tests, builds once, and publishes the entire `dist` directory. No runtime router is needed.
- Existing Hearts saves must still load after the shared-module move. Do not require players to re-create their roster or restart Hearts. Keep identifiers, serialized card shapes, existing `version` values and storage keys unchanged.

## Setup and tournament lifecycle

Select 2–8 active players from the shared roster, with inline Add Player and access to the shared Players screen. No duplicate ID may occupy two seats; seat order is clockwise. A player renamed in the roster keeps the same ID; active tournaments use a name snapshot until a new tournament begins. Choose starting chips and big blind as positive whole numbers; prevent a tournament from starting with a stack smaller than the big blind. The first dealer is chosen randomly among entrants, using the action’s seed. The button moves clockwise to the next player with chips for each subsequent hand. Provide a confirmed abandon/new-tournament action; abandoned tournaments are not recorded as wins.

At hand start, snapshot the current big/small blind and deal a fresh, seeded, shuffled deck. Exclude eliminated players. Each live player receives two private cards. Post blinds up to the amount a player can afford (a short blind can be all-in); those bets count toward their preflop contribution. The pot display includes posted blinds. The remainder of the deck is retained to burn one card before three flop cards, one before the turn, and one before the river. Never repeat a card. Button/blind positions:

- With three or more players: the next live seat after the dealer posts the small blind, the next live seat posts the big blind, the next live seat after the big blind acts first preflop; the first live seat after the dealer acts first on later streets.
- Heads-up: the dealer posts the small blind and acts first preflop; the opponent posts the big blind and acts first on all later streets.
- The big blind retains the option to check or raise preflop if no one has raised. If blinds are short, the minimum *full* bet/raise is still based on the hand’s big blind, not the amount actually posted.

Play continues through preflop → flop → turn → river → showdown (or immediate uncontested award if everyone else folds). Do not reveal an opponent’s hole cards in handoff, action, or uncontested-win screens. A device handoff hides the previous hand and shows a button naming the next player; only their own two cards appear after they explicitly reveal them. A reload always returns to a hidden-hole-card gate. Board, stacks, pot, street, button, blinds, and contributions are public information.

After payout, show the hand result and updated stacks; allow the next hand. Eliminate zero-stack players; with one player remaining, show the tournament winner. If a player cannot act because they are all-in, skip them. When remaining players cannot make a further bet (all are all-in, or only one has chips and no one can call a bet), run out the board automatically and proceed to showdown. Do not require meaningless checks to reveal the remaining cards.

## No-limit betting

For each street, track each player's stack, contribution on this street, cumulative contribution in the hand, folded/all-in status, most recent full raise size, and whose action is outstanding. The current bet is the highest street contribution. The amount to call is `min(stack, currentBet - ownStreetContribution)`; a short call becomes all-in. The UI offers only legal Check (nothing to call), Call (something to call), Fold (when facing action), Bet/Raise with amount input, and All-in. All actions require confirmation before changing cards or chips; the engine validates action type, turn, amount, stack, and minimum raise. Disallow zero/negative/decimal amounts and amounts greater than a stack. A player who checks when no bet is due can subsequently face a raise in the same street.

When opening a street, the minimum full bet is the hand's big blind. A full raise must increase the current bet by at least the previous full bet/raise increment. A short all-in bet or raise below that minimum is allowed when the player commits their entire remaining stack. It changes what other players owe, but **does not reopen raising** to a player who has already acted since the last full raise. A full raise reopens action. A betting round ends only when every non-folded, non-all-in player has had the chance to act and matched the current bet, or when no further betting is possible. Do not permit an uncalled excess bet to become part of a contested pot; refund the excess to its contributor before awards. Chip conservation applies after every action and payout: stacks plus all live hand contributions always equal the tournament's initial chips.

## Showdown and side pots

If only one player remains un-folded, award all committed chips (after any uncalled refund) to them without exposing any hole cards. Otherwise reveal *all* remaining players' two hole cards, including all-in players, alongside five public board cards. Evaluate the strongest five-card combination from each player’s seven cards; show the **actual five selected cards** and a readable hand label (e.g. “two pair, aces and queens”). Compare standard high poker hands from high card up to royal/straight flush. An ace can be low in a wheel straight; tie-break all categories by relevant ranks, not suits. Equal-strength hands tie even if their chosen five cards differ by suit.

Build main and side pots from sorted contribution levels. A folded player contributes chips but cannot win. At each level only players whose contributions reach that level are eligible; for each pot select the best hand among its eligible, non-folded players. Split equally among tied winners. Allocate odd chips, one at a time, to eligible winners in clockwise order starting immediately left of the dealer. Apply payouts atomically and assert total chip conservation. Show each pot’s amount and winner(s) and each player’s resulting stack. The two-player showdown displays both players, both best-five hands, and the winner or a tie; the same presentation scales to 3–8 players.

## Blind changes, persistence, and errors

Provide a visible “Blinds” control at any point during a tournament, including handoff screens. Editing the big blind writes a pending value to `poker.settings` immediately; the current hand continues using its immutable blind snapshot and the control labels the pending value “next hand.” The new value is applied when dealing the next hand, recalculating `ceil(bigBlind / 2)`. Reject invalid entries with a clear error. A completed tournament can start a new tournament with the shared roster.

Autosave the tournament after every confirmed action using `poker.tournament`, separately from roster, settings, and Hearts. Include a version field and validate a loaded snapshot (player IDs, deck/card uniqueness, stacks, contributions, phases, turn/seat indices, board length, totals). If invalid, discard only the poker tournament and show setup; do not delete the roster, blinds, or Hearts state. A reload offers Resume or New Tournament with private cards hidden. If storage fails, keep play working in memory and show a non-blocking “not saved” warning. Presentation-only state such as a raised card or the current modal is not persisted. Engine actions rejected as illegal leave the exact state object unchanged.

## Screens and presentation

The poker app uses the existing card-face visual language and felt theme while accommodating up to eight seats on a portrait phone: a scrollable player list or responsive table is preferable to tiny overlapping seat labels. Main screens are Setup/Players, handoff and private action, public betting table, street/board reveal, uncontested hand result, showdown with ranked best-five cards and pot payouts, between-hands result, and tournament winner. Buttons have readable action amounts and a clearly labeled confirm step. Board cards and publicly committed bets stay visible throughout a hand; private cards never appear before their owner reveals them or before showdown. The blind settings control is reachable without leaking private cards. Provide reduced-motion behavior for any animation.

## Testing and release checks

- Shared code move: run all existing Hearts tests unchanged (plus smoke and persistence tests for existing Hearts saves and roster names). Confirm both games read and write the same roster IDs.
- Poker engine: seeded unique dealing and burn cards; normal and heads-up dealer/blind/action order; preflop big-blind option; street termination; fold, check, call, full/short all-in raise, raise reopening; blinds changed mid-hand; chip conservation on each action; main and multiway side pots, folded contributions, uncalled-bet refund, tied pots and odd-chip distribution.
- Evaluator: every hand category, rank tie-breakers, wheel, board-only ties, best five from seven, and distinct hands whose suits differ but ranks tie.
- UI/persistence: gate on every pass/reload, two-player showdown displays both hole cards and exact best five, settings changed mid-hand apply only next hand, elimination and tournament completion, corrupt poker save does not affect Hearts or roster, storage failure warning.
- Build: both `/offline-hearts/` and `/offline-hearts/offline-texas-holdem/` load from the static `dist` tree with correct assets/manifests and offline navigation. Verify at phone viewport widths and test offline navigation after first load; physical iOS Home Screen testing must be reported separately if not available. Run full test suite and production build before claiming completion.
